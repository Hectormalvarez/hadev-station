# US-004 — Discoverability: wrong arguments get help, not an ansible error

**Status:** Draft
**Epic:** Run Confidence

## Description

As a developer running `setup.sh`,
I want invalid or unrecognized arguments to show the script's usage help with a short explanation,
so that I never have to read an Ansible error (or the source) to find out what the script accepts.

## Context & Scope

**In-scope:**
- Unknown or malformed arguments produce a short "unrecognized option" message plus the usage help, and exit non-zero
- `--help` / `-h` remain the canonical full help (content unchanged in scope)
- Documented Ansible pass-through options keep working untouched

**Out-of-scope (MVP trims):**
- Interactive tag menu — cut in US-002, stays cut
- Validating tag *values* (e.g. rejecting a typo'd tag name) — the playbook already no-ops on unknown tags per US-001; duplicating that check adds a second source of truth
- Rewriting help content or adding man pages
- Any change to how valid arguments are forwarded

## Acceptance Criteria

1. **Given** the user runs the script with an unrecognized option (e.g. `./setup.sh --tagz "dotfiles"`), **When** it starts, **Then** they see a one-line "unrecognized option" message followed by the usage help, and it exits non-zero without running the playbook.
2. **Given** the user runs the script with documented Ansible options (e.g. `--syntax-check`, `--tags "..."`, `--list-tags`), **When** it starts, **Then** behavior is unchanged — no false rejection.
3. **Given** the user runs `--help` or `-h`, **When** it starts, **Then** the full usage help is shown and it exits successfully.
4. **Edge case:** **Given** the script is invoked with an option that only Ansible understands but is malformed for that tool (e.g. `--tags` with no value), **Then** the script forwards it untouched and the resulting error comes from Ansible, not from new validation that guesses wrong.
