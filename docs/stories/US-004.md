# US-004 — Discoverability: wrong arguments get help, not an ansible error

**Status:** Approved
**Epic:** Run Confidence

## Description

As a developer running `setup.sh`,
I want invalid or unrecognized arguments to show the script's usage help with a short explanation,
so that I never have to read an Ansible error (or the source) to find out what the script accepts.

## Context & Scope

**In-scope:**
- Unknown or malformed arguments produce a short "unrecognized option" message plus the usage help, and exit non-zero
- `--help` / `-h` remain the canonical full help (content unchanged in scope)
- Documented Ansible pass-through options keep working untouched

**Out-of-scope (MVP trims):**
- Interactive tag menu — cut in US-002, stays cut
- Validating tag *values* (e.g. rejecting a typo'd tag name) — the playbook already no-ops on unknown tags per US-001; duplicating that check adds a second source of truth
- Rewriting help content or adding man pages
- Any change to how valid arguments are forwarded

## Acceptance Criteria

1. **Given** the user runs the script with an unrecognized option (e.g. `./setup.sh --tagz "dotfiles"`), **When** it starts, **Then** they see a one-line "unrecognized option" message followed by the usage help, and it exits non-zero without running the playbook.
2. **Given** the user runs the script with documented Ansible options (e.g. `--syntax-check`, `--tags "..."`, `--list-tags`), **When** it starts, **Then** behavior is unchanged — no false rejection.
3. **Given** the user runs `--help` or `-h`, **When** it starts, **Then** the full usage help is shown and it exits successfully.
4. **Edge case:** **Given** the script is invoked with an option that only Ansible understands but is malformed for that tool (e.g. `--tags` with no value), **Then** the script forwards it untouched and the resulting error comes from Ansible, not from new validation that guesses wrong.

## Technical Guidance

Defined at the Architect gate (2026-09-13):

- **Target file: `setup.sh` only.** No playbook, role, or workflow changes.
- **Validation strategy: static, name-level allowlist.** Every `-`-prefixed
  argument is checked against one commented array in `setup.sh`:
  script-owned (`-h`, `--help`), documented pass-through (`--syntax-check`,
  `--list-tags`, `--list-hosts`, `--tags`/`-t`), and common ansible-playbook
  options with aliases (`--check`/`-C`, `--diff`/`-D`, `--limit`/`-l`,
  `--skip-tags`, `--start-at-task`, `--step`, `--vault-id`,
  `--vault-password-file`, `-v` through `-vvvv`). Dynamic validation against
  `ansible-playbook --help` output was considered and rejected: parsing help
  text is brittle and its format is not an API.
- **Values and arity are never validated** (AC 4): `--tags` with no value is
  forwarded untouched and ansible reports the error; non-dash arguments are
  forwarded untouched. Only option *names* are judged.
- **Placement:** validation runs first in Main, before `install_ansible` and
  `ensure_config` — garbage arguments fail fast with exit 2 (distinct from
  1 = config, 4 = ansible) regardless of machine state. Use an explicit
  `exit 2` in the validator, not a failing command under `set -e`.
- **On rejection:** one line `Unrecognized option: --tagz`, then the full
  usage help, then exit 2, without running anything.
- **Forbidden moves:** no tag-value validation (US-001 already no-ops unknown
  tags — no second source of truth), no interactive menu, no output
  reformatting, no playbook changes.
- **Known deviation needing human approval:** the help currently states "All
  arguments are passed through to ansible-playbook untouched" (line 93). This
  change breaks that promise, so the story's "help content unchanged" trim is
  amended to allow a **single-line correction** of that sentence; nothing else
  in the help text changes.
