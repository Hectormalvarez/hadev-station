# US-002 — Know before it changes: pre-flight summary and destructive-run confirmation

**Status:** Draft
**Epic:** Run Confidence

## Description

As a developer running `setup.sh` on my workstation,
I want a summary of what a run will change before it changes, and a confirmation gate before my personal files are overwritten,
so that I always know the blast radius of any run and never lose personal config by accident.

## Context & Scope

**In-scope:**
- A pre-flight summary printed **before every mutating run**: which areas (tags/roles) will run and whether personal files would be touched
- A `y/N` confirmation gate that appears **only** when personal dotfiles or `config.yml` would be overwritten
- A `--yes` flag to skip the gate for scripted/non-interactive runs
- Parse-only invocations (`--syntax-check`, `--list-tags`, `--list-hosts`) never summarize and never prompt
- First-run behavior unchanged (`config.yml` bootstrap-and-exit stays as-is)

**Out-of-scope (MVP trims):**
- Interactive tag menu / CLI redesign — `--tags` + help already work; doesn't serve this outcome
- Dry-run-by-default with opt-in `--apply` — too much friction for a personal bootstrap
- Friendly failure/recovery UX and traceback handling — separate candidate story, deliberately not diluted into this one
- Colored/rich output, post-run change reports — polish, cut
- Any playbook/role behavior change — this story only changes how a run *starts*, not what it does

## Acceptance Criteria

1. **Given** any mutating run, **When** the user starts it, **Then** a pre-flight summary (areas to run, whether personal files would be touched) is shown before any change occurs.
2. **Given** a run that would overwrite personal dotfiles or `config.yml`, **When** it starts, **Then** the user is asked to confirm (`y/N`) and nothing changes unless they explicitly answer yes.
3. **Given** a run that would *not* touch personal files (e.g. a tools-only tag), **When** it starts, **Then** it proceeds without any prompt.
4. **Given** the `--yes` flag, **When** any run starts, **Then** no prompt appears and the run proceeds exactly as before — existing scripted usage stays backwards compatible.
5. **Given** a parse-only invocation (`--syntax-check`, `--list-tags`, `--list-hosts`), **When** run, **Then** no summary and no prompt appear and output is unchanged.
6. **Edge case:** **Given** a non-interactive environment (no TTY) without `--yes` on a run that would overwrite personal files, **Then** the run aborts safely with a clear message rather than hanging or proceeding unconfirmed.

## Technical Guidance

Defined at the Architect gate (2026-09-14):

- **Target file: `setup.sh` only.** No playbook/role changes.
- **Gate condition (verified against ADR-002):** only `dotfiles`, `terminal`,
  and unfiltered full runs regenerate `~/.bashrc_extras`/`~/.tmux.conf` — the
  gate keys on exactly those. `config.yml` is **never overwritten** after the
  first-run bootstrap (which creates-and-exits before any pre-flight), so no
  gate is needed for it — a deliberate, recorded simplification of AC 2.
- **Safe defaults:** a dangling or unparseable `--tags` value is treated as a
  full run (i.e. it prompts); the prompt default is **N**.
- **`--yes` is script-consumed and never forwarded** (ansible has no such
  option); it is added to `KNOWN_OPTIONS` and stripped before validation.
  Decline exits 1 with "nothing was changed"; no-TTY abort exits 1 with the
  `--yes` hint.
- **Placement:** pre-flight runs after `ensure_config` (a broken config is
  never prompted about) and is skipped entirely for parse-only runs.
- **Approved deviation:** one `--yes` example line added to the usage help
  (discoverability; consistent with US-004's contract).
