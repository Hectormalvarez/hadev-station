# US-003 — Failure & recovery UX: know what broke and what to do next

**Status:** Draft
**Epic:** Run Confidence

## Description

As a developer running `setup.sh` on my workstation,
I want a clear, human message when a run fails — what broke, whether my machine is left half-configured, and what to do next,
so that a failure is a pause I can recover from, not a traceback I have to decode.

## Context & Scope

**In-scope:**
- A clear, friendly failure message whenever the run stops unsuccessfully (including the Ansible install step), replacing the raw traceback as the *first* thing the user sees
- Each failure message states: what failed, and a concrete next step
- Explicit reassurance when a failure leaves partial work: the user is told their setup is safe to re-run after fixing the cause — no half-broken machine anxiety
- Failure exit is distinguishable from success (non-zero exit is preserved; no "✅ Setup Complete!" on failure)

**Out-of-scope (MVP trims):**
- Automatically retrying, rolling back, or "fixing" failures — the script diagnoses, it doesn't heal
- Deep traceback analysis or reformatting all Ansible output — the raw detail must remain available below the friendly message, not be hidden
- A dedicated troubleshooting doc or website — messages must be self-contained
- Colored/rich output — polish, still cut
- Any playbook/role behavior change — this story only changes how failure *feels*, not what runs

## Acceptance Criteria

1. **Given** the playbook fails mid-run, **When** the script exits, **Then** the user sees a short human-readable failure message — what failed and a suggested next step — with the underlying Ansible error still visible in the output.
2. **Given** Ansible itself is missing and its installation fails (e.g. no network), **When** the script exits, **Then** the user gets a message naming the install step and its likely cause, not a silent apt error.
3. **Given** a run fails partway through, **When** the user reads the failure message, **Then** they are explicitly told the setup is safe to re-run after addressing the cause — nothing needs manual un-doing.
4. **Given** any failure, **When** the script exits, **Then** the exit code is non-zero and the "✅ Setup Complete!" message does not appear.
5. **Edge case:** **Given** the user's `config.yml` is broken (unparsable), **When** they run the script, **Then** they are told the config file is the problem and where it is, rather than a generic playbook parse error.

## Technical Guidance

Resolved at the Architect gate (see `docs/decisions/ADR-002.md`, Proposed):

- **Target file: `setup.sh` only.** Playbook, roles, and templates are
  forbidden to change in this story.
- **Centralize failure handling with a bash `trap` on ERR** (the script
  already runs `set -euo pipefail`): one failure reporter serves all failure
  paths; no scattered per-step error handling. Raw Ansible/apt output stays
  visible — never redirect or suppress it.
- **T1 (playbook failure):** the trap reporter names the failed step (the
  playbook run), suggests re-running after fixing the cause, and includes
  ADR-002's caveat: playbook-managed dotfiles (`~/.bashrc_extras`,
  `~/.tmux.conf`) are regenerated from templates, so hand-edits are not
  preserved. Preserve the playbook's exit code where practical (non-zero
  either way).
- **T2 (Ansible install failure):** wrap the install step so its failure
  names the step and the likely cause (network/apt). No output suppression.
- **T3 (broken config):** validate `config.yml` parseability early, before
  the run, using only already-present tooling (reuse Ansible itself for the
  parse — no new dependencies, no elevation). On failure, point at the file.
  Must never write to `config.yml`.
- **T4 (exit discipline):** keep `set -euo pipefail`; the success line is
  reached only on success; every trap/exit path is non-zero.
- **Wording honesty (from audit):** messages name *which step* failed, never
  a root cause; never echo `config.yml` contents.
- **Forbidden moves:** no retry/rollback logic, no output reformatting, no
  colored output, no changes to `become`/tags/task ordering (ADR-001).
