# US-005 — Post-run feedback: a completion summary that says what happened

**Status:** Approved
**Epic:** Run Confidence

## Description

As a developer running `setup.sh`,
I want a brief completion summary telling me which areas ran and what changed (or that nothing changed),
so that a finished run confirms reality instead of just printing a green checkmark.

## Context & Scope

**In-scope:**
- On success, a short summary after the run: which tags/areas ran and whether anything changed
- Explicit "nothing changed" feedback when a re-run makes no changes (the common update case)
- Works identically for full runs and partial (`--tags`) runs

**Out-of-scope (MVP trims):**
- Per-task change listings or a change log file — area-level truth is enough for confidence
- Colored/rich output — still cut
- Failure-case summaries — failure UX is US-003's job; this story is success-only
- Any change to what the playbook does or reports internally beyond what the script can already observe

## Acceptance Criteria

1. **Given** a successful run that made changes, **When** it completes, **Then** the user sees a summary naming the areas that ran and indicating that changes were made.
2. **Given** a successful run that changed nothing (re-run on an up-to-date machine), **When** it completes, **Then** the user is explicitly told nothing changed.
3. **Given** a partial run via `--tags`, **When** it completes successfully, **Then** the summary reflects only the tags that were requested, not the whole setup.
4. **Edge case:** **Given** the user passes Ansible a combination the script can't summarize (e.g. complex options), **Then** the script degrades gracefully — it shows a generic success message rather than a wrong or missing summary.

## Technical Guidance

Defined at the Architect gate (2026-09-14):

- **Target file: `setup.sh` only.** No playbook/role changes.
- **Observation mechanism:** the mutating branch of `run_playbook()` tees
  ansible output to a mktemp file; `summarize_run()` parses only the final
  `PLAY RECAP` line for `changed=N`. This is success-side observation and
  does not violate US-003's "no output parsing for failure diagnosis" rule —
  failures still flow through the untouched ERR-trap reporter.
- **Wording:** `changed=0` → explicit "nothing changed — already up to
  date"; `changed>0` → "N change(s) applied to <area>"; recap missing or
  unparseable → the original generic "✅ Setup Complete!" (degrade, never
  claim wrongly). The area string comes from US-002's `run_plan()`.
- **Pipeline hazard:** recapping via `cmd | tee` re-enters the ERR trap in
  the pipeline subshell and would print the failure message twice (the
  US-003 advisory made real). The trap is disarmed around the pipeline and
  failure is handled with an explicit `if`, calling the reporter once.
- **Scope of summary:** mutating runs only; parse-only runs keep the current
  behavior. The recap temp file is removed on success and in
  `report_failure()`.
