# ADR-002: Playbook re-run safety (convergence guarantee)

**Status:** Proposed

## Context & Problem Statement

US-003 (failure & recovery UX) ships a user-facing message promising that a
failed run can simply be re-run after fixing the cause. That promise is only
honest if the playbook is convergent: no task may double-apply destructively
or corrupt state on re-run. A full idempotency audit of `local.yml` pre_tasks
and all six roles (`core`, `system`, `terminal`, `languages`, `docker`,
`virtualization`) was performed to verify this before the message ships.

## Decision Drivers

- User-facing honesty: the reassurance text must match verified reality
- Data-safety: distinguish "safe to re-run" from "preserves hand-edits"
- No new tooling or collections
- Consistency with US-002's destructive-change gate (dotfiles overwrite)

## Considered Options

1. **Ship the reassurance based on assumption** — idempotency was a design
   goal but never audited; promising it unverified risks dishonest messaging.
   Rejected.
2. **Soften the message to "usually safe to re-run"** — vague reassurance
   without a verified basis. Rejected as unfalsifiable and unhelpful.
3. **Audit every task, then declare convergence with explicit caveats** —
   chosen.

## Decision Outcome

The playbook is declared **convergent**: every state-changing task is either a
native idempotent module (`file`, `apt`/`package`, `service`, `user` with
`append: yes`, `git_config`, `openssh_keypair` without force,
`apt_repository`) or a correctly guarded `shell`/`command` (`creates:`,
`changed_when: false`, or a `when:` check — e.g. the vagrant plugin installs).
A failed run leaves the machine converged-or-partially-converged; re-running
converges it without data loss. User-facing messages may promise re-run
safety.

**Explicit caveats (must be reflected where users are told):**
- `~/.bashrc_extras` and `~/.tmux.conf` are **playbook-managed** and
  regenerated from templates on every run — manual edits to them are
  intentionally discarded. `~/.tmux.conf` had no existence guard before this
  audit: a pre-existing personal tmux config is destroyed on first run with
  no backup (accepted for this personal playbook; do not promise
  hand-edit preservation anywhere).
- The HashiCorp signing key fetch (`get_url force: true` in `local.yml`
  pre_tasks and `roles/virtualization`) always reports `changed` — cosmetic
  only; it means a converged run is never 100% "green".

**Positive consequences:** re-run safety is a verified, documented property
rather than an assumption; US-003's messaging has an honest basis; US-002's
destructive-change gate now has a verified list of exactly which files
qualify as destructive (`~/.bashrc_extras`, `~/.tmux.conf`).

**Negative consequences:** the convergence guarantee must be maintained —
any new task must keep the audit's guard patterns (constraint below), and
nothing enforces this automatically until CI checks land (backlog US-006).
The two managed dotfiles remain silent hand-edit eaters by design.

## Technical Implementation Guidance

- Any new task must be re-run safe: idempotent modules only, or
  `shell`/`command` with `creates:`, `changed_when: false`, or a `when:`
  guard — consistent with ADR-001's constraint that guards not be altered.
- Do not add `force: true` to tasks targeting user files.
- Failure/recovery messaging must name the failed *step*, never claim a root
  cause from parsing Ansible output.
- Messages must never echo `config.yml` contents (personal data).
- If a task violates convergence later, this ADR must be updated or
  superseded before any user-facing text relies on it.
